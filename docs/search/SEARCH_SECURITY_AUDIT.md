## SQL / search injection

**Tested directly, not assumed.** 8 distinct payloads sent as the live
`q` parameter against `GET /api/v1/search`: classic `' OR '1'='1`,
`'; DROP TABLE jobs; --`, quote-based variants, URL-encoded injection,
`<script>` tags, template-injection syntax (`{{7*7}}`), and a JNDI-style
payload. Every one returned `200` with a normal (usually empty)
result set â€” none 500'd, none returned every row (which would indicate
the filter was bypassed rather than treated as literal text).

**Why this holds structurally, not just by luck:** every search query
path (`app.search.provider.DatabaseSearchProvider`) builds its query
via SQLAlchemy's `.ilike()`/`.where()` â€” confirmed by reading every
line that touches `SearchIndexDocument` â€” never via `text()` with
string-concatenated SQL. A query value like `f"%{term}%"` becomes a
*bound parameter*, not interpolated SQL text, regardless of the
f-string used to build the wildcard pattern.

## IDOR

- A draft job (recruiter-created, `draft: True`) never appears in
  anonymous search results â€” verified.
- Recruiter A's unpublished/draft job is not fetchable or editable by
  Recruiter B (`GET`/`PUT /recruiter/jobs/{id}` both 404, not 403 â€”
  existence isn't leaked either) â€” verified.
- Recommendation preferences are per-user; user B reading their own
  preferences never sees user A's saved values â€” verified.
- `GET /job-recommendations/{job_id}/explanation` requires
  authentication (401/403 without a token) â€” verified.
- `GET /job-recommendations/analytics` is admin-only â€” verified.

## Edge-case / malformed input handling

Empty query, whitespace-only query, unicode/emoji, a 500-character

## RBAC / visibility

Every search request runs through a real `SearchActor` built from the
requesting user (or an anonymous actor) â€” never an elevated actor â€”
so the same visibility rule applies everywhere: only `status ==
"published"` rows are visible to a non-owner, and expired-deadline
rows are excluded explicitly (deadline passing does not flip `status`
anywhere in this codebase). This is the identical rule
`app.recommendations.retrieval` reuses for Stage-1 recommendation
retrieval â€” one enforcement point, not two.

## Failure handling

Best-effort search-analytics logging (`app.search.service._log`) had
no error handling â€” **found and fixed this release**: a logging
failure (DB hiccup, malformed shape) was propagating as an unhandled
500 on the actual search response. Now wrapped and logged as a
warning; verified with a test that forces the underlying logger to
raise and confirms the search response is still `200`.
