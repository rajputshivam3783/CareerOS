## Default grants by role

`candidate` and `recruiter` have no permissions in this (dot-namespaced)
catalog by default â€” their capabilities are governed by the original
V16 colon-namespaced `ROLE_PERMISSIONS` (`applications:manage_own`,
`saved_jobs:manage_own`, `resume:manage_own` for candidate;
`jobs:manage_own`, `applicants:view_own_jobs`,
`applicants:update_status_own_jobs` for recruiter), unchanged by this pass.

| Role | Default dot-namespaced permissions |
|---|---|
| `recruiter_manager` | `jobs.create`, `jobs.update`, `applications.review` |
| `recruiter_admin` | `jobs.create`, `jobs.update`, `jobs.delete`, `applications.review`, `applications.export` |
| `support_admin` | `users.read`, `sessions.read`, `admin.audit.read`, `recruiters.approve`, `users.reset_password` |
| `system_admin` | Everything in the catalog *except* `users.delete` |
| `admin` | Everything in the catalog |
| `super_admin` | Everything in the catalog |

Note: `users.delete` is in the catalog (for future use â€” e.g. GDPR/data-
deletion tooling) but is not granted as a default to any role below
`admin`, and no route in this pass calls `require_permission_dual("users.delete")` â€”
there is no user-deletion endpoint yet. It exists in the catalog only so
adding one later doesn't require inventing a new permission string.

## Changing a role's permissions

No code change or deploy is required:

```
POST /admin/rbac/roles/{role}/grant   {"permission": "analytics.read"}
POST /admin/rbac/roles/{role}/revoke  {"permission": "analytics.read"}
```

Both require the `roles.manage` permission (or the shared admin key).
Both take effect on every *subsequent* request immediately â€” including
for an already-issued access token, since permission checks are
evaluated per-request against the database, not cached in the token.
See `RBAC_ARCHITECTURE.md`'s "Permission resolution" section for the
exact merge rule, and `tests/test_v17_3_rbac.py`'s
`test_a_jwt_gains_a_granted_permission_without_relogging_in` for the
behavior this guarantees.
