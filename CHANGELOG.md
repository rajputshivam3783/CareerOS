| V25.4 | Advanced AI Career Agent & Automation — a candidate-facing, user-controlled AI agent (`/career-agent`) built entirely on reuse: sixteen tools wrap V21.1 search, V21 recommendations, V22.1 applications/tasks/timeline, V20.4/V22.4 interview prep and follow-up drafting, V20.2 resume AI, V25.3 skill-gap/learning-path/career-intelligence, and V23.1 notifications — no tool re-implements search, ranking, matching, skill-gap, or eligibility logic. Hard architectural rule: the LLM never talks to the database — `app/career_agent/intent.py` asks the model to choose at most one tool from a fixed whitelist (`tool_registry.py`) and propose its parameters as JSON; `validate_call()` rejects any unknown tool, unexpected parameter, or missing required parameter before a single service function runs, and a deterministic keyword fast-path skips the AI call entirely for common phrasings. A controlled state machine (`state_machine.py`: IDLE→UNDERSTANDING→PLANNING→WAITING_FOR_CONFIRMATION/EXECUTING→COMPLETED/FAILED, illegal transitions raise) guarantees a WRITE or HIGH_RISK tool cannot execute without passing through an explicit, separate confirm request (`POST /career-agent/actions/{id}/confirm`) — confirming an already-settled action is rejected (409), not re-executed, which is the idempotency guarantee against replay/duplicate execution. The two HIGH_RISK tools (`submit_application`, `send_recruiter_message`) are honest about CareerOS's actual capabilities: neither has a real submission/send integration yet, so both prepare information (an apply link, a drafted follow-up) and explicitly say nothing was submitted/sent — never a fabricated success. Four new tables (`career_agent_conversations/messages/actions/preferences`), deliberately not a reuse of V20.1's `ai_conversations/ai_messages` (an agent turn's metadata — which tool ran, which action it produced — has no column on the generic chat schema, and a pending-confirmation write action has no analogue in a plain chat log at all). Reuses V20.3 Career Copilot's context engine and prompt-injection defenses (`context_engine`, `wrap_untrusted`) rather than rebuilding grounding/untrusted-content handling from scratch; `/career-copilot` is unchanged and coexists with the new `/career-agent`. Proactive notifications and a deterministic "Career Brief" reuse V23.1's `create_notification`/dedupe-key idempotency rather than building a second notification system. New frontend route `/career-agent` (chat with inline confirm/cancel, a Pending Actions center, history, brief, preferences) matching existing page conventions. ~30 new tests written — **not executed**: no network access in the authoring sandbox; every referenced service function signature and model field was instead checked directly against source, catching one real bug before it shipped (a raw `datetime` in a tool result breaking `json.dumps` — fixed with `default=str`). See [`docs/V25_4_AI_CAREER_AGENT.md`](./docs/V25_4_AI_CAREER_AGENT.md) and [`V25_4_TEST_REPORT.md`](./V25_4_TEST_REPORT.md). |
| V25.3 | Data Intelligence, Career & Market Analytics — a deterministic analytics layer over existing CareerOS data, built to reuse rather than duplicate: organization hiring intelligence calls V24.4's `recruiter_analytics.service` unmodified with the organization's own member ids; the AI layer calls V24.4's `_generate_grounded` cache/guard pipeline directly with new prompts; skill canonicalization goes through V20.5's alias catalog; platform counts call V25.2's `dashboard_metrics` unchanged. New `app/intelligence/` package: `corpus.py` (one filtered job/application loader every analytic shares — published jobs only, `published_at`-windowed, capped materialization), `skills.py` (document-frequency skill counting from `jobs.skills` only — description text is never scanned, so a job saying 'no Java required' can't count as Java demand), `roles.py` (target-role resolution restricted to explicit selection, saved career preference, or profile — never inferred), `candidate.py`/`market.py`/`organization.py`/`platform_intel.py` (the five views), `ai.py` (explains already-computed numbers, never calculates), `quality/` (18 declarative data-quality rules with a generic read-only runner — no endpoint modifies an inspected record; the only write is an administrator's own triage note, audited). Market intelligence carries an explicit `scope: careeros_platform` label on every response rather than describing platform activity as an external market statistic, since none is available; salary is reported as disclosure coverage only, never as fabricated analytics, since `jobs.salary` is unvalidated free text. Every skill-coverage and gap figure carries its own formula string — no opaque career score anywhere. Three sample-size thresholds (corpus/trend/privacy-group) are V25.2 typed platform settings, not hardcoded, and every suppression is reported with its sample size rather than silently omitted. Two real bugs were found and fixed during implementation before being run: V20.5's `resolve_many()` silently drops a second alias of an already-resolved skill within one batch (e.g. Postgres + PostgreSQL together), fixed by resolving against the raw lookup map directly and regression-tested; and a reused AI-cache `scope_type` value exceeded its `String(20)` column (would fail on PostgreSQL, not SQLite), shortened and documented on the model. Organization-intelligence and career-intelligence authorization is structural — the career router accepts no identity parameter at all, and organization routes depend on V25.1's membership check, which 404s a non-member and logs the attempt. One new table (`data_quality_issue_states`); no new analytics event table, since everything section 16 lists is already recorded by existing V19–V23 event tables; no aggregate/snapshot tables or materialized views, since every aggregate is a bounded, indexed real-time query. Four new frontend screens (`/career-intelligence`, `/recruiter/intelligence`, `/admin/intelligence`, `/admin/data-quality`). 54 new tests written — **not executed**: no network access in the authoring sandbox; every referenced model field, function signature and column constraint was instead checked directly against source (catching the two bugs above, plus a test-fixture dedup collision and an `id(client)`-reuse flakiness bug in the tests themselves) — backend tests, frontend build, lint and type-check are reported NOT VERIFIED. See [`docs/V25_3_DATA_INTELLIGENCE.md`](./docs/V25_3_DATA_INTELLIGENCE.md) and [`V25_3_TEST_REPORT.md`](./V25_3_TEST_REPORT.md). |
